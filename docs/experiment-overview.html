The experiment
1 · The question
If a model learns something, then seems to forget it, does it learn it again faster than a model that never knew it?

Analogy: you learned French at school, then spoke only Spanish for years. Is relearning French easier for you than for someone who never studied it? And is that because you remember French, or just because you have studied a language before?

2 · The three models (arms)
A · learned it

Pretrained on CIFAR-10

The data we care about. In the analogy, studied French.

B · never learned

Random weights

No pretraining at all. In the analogy, never studied any language.

C · learned something similar

Pretrained on CIFAR-100

Similar photos, different data. In the analogy, studied Italian.

Why C exists: A beating B could just mean any pretraining helps. C has similar pretraining without CIFAR-10, so if A also beats C, A remembers CIFAR-10 specifically.

4 · The two relearning subsets

"A-seen" is about where the images come from

Stage 3 runs twice per arm, on two different 5k CIFAR-10 subsets. They are named after A, because A is the only arm that ever trained on CIFAR-10.

SubsetABC
A-seen 5kseen in stage 1newnew
never-seen 5knewnewnew

Why B and C run on both subsets

They are the control for subset difficulty. If A relearns faster on A-seen than on never-seen, it could be memory of those images, or A-seen could just be an easier subset.

B and C can't remember those images, so any gap they show between the two subsets comes from difficulty alone.

How the memory effect is computed

gap = result on A-seen − result on never-seen

memory effect = gap(A) − gap(B)

Example: gap(A) = +4 points, gap(B) = +1 point. Then 3 points are A remembering those images, and 1 point is A-seen simply being easier.

6 · The check before relearning

Does A only look forgotten?

Old-head test (A only)

Put A's saved CIFAR-10 head back on its post-SVHN backbone and test it.

Why: shows how forgotten A looks. Should be close to 10% (chance) if stage 2 worked.

7 · The baseline (step 4)

One normal training run before the real experiment

The baseline is a single ResNet-18 trained from scratch on the 40k CIFAR-10 pretrain pool. It is not one of the arms and not part of the comparison. It is a test run that tells you whether the code works, what "fully learned" looks like, and how long everything will take. Trained exactly like stage 1, it also becomes A's stage 1 for seed 1.

How to train it

SettingValueWhy
Data40k CIFAR-10 pretrain pool from the saved split (step 2)Same data A uses in stage 1; held-out images stay unseen.
ModelResNet-18, CIFAR stem (3×3 stride-1 first conv, no max-pool), backbone and head as separate partsThe ImageNet stem shrinks 32×32 images too much. Separate parts are needed for head swaps later.
AugmentationRandom crop 32 (padding 4) + horizontal flip; none at evaluationThe standard CIFAR recipe (checked in section 13).
NormalizationCIFAR-10 mean and stdThe same values every stage will use.
OptimizerSGD, momentum 0.9, weight decay 5e-4, batch size 128The fixed recipe for all stages.
Learning rateCosine decay from 0.1The stage-1 schedule.
LengthA fixed number of epochs (e.g. 100–200), chosen before startingMust equal the stage-1 length for A and C, or the checkpoint can't be reused.
CheckpointThe final one, after the last epochNever the "best test epoch": that would use the test set to make a decision.

How to run it

  • Smoke test first: 1 epoch, to catch crashes, shape errors and MPS problems in minutes.
  • Then the full run with the fixed number of epochs.
  • At the end: save the checkpoint (backbone + CIFAR-10 head, in one file), and run the linear probe once to test the probe code too.
  • If MPS fails, stop and report it instead of switching device.

What to record

  • Per epoch: train loss and accuracy, CIFAR-10 test loss and accuracy, epoch time.
  • Final: test accuracy, total time, saved checkpoint.
  • Probe accuracy on the final backbone (should be close to the full model's accuracy).

Reading the result

You seeMeaningNext

Test accuracy well below ~90%Likely a bug: ImageNet stem, wrong normalization, missing augmentation, or LR schedule not applied.Fix and rerun before anything else.

9 · What to measure

Every metric, and the question it answers

Each metric is here to answer one question. The tables say which question, and how to read the number.

Key metric: the CIFAR-10 probe at checkpoints

The problem: B and C can't be scored on CIFAR-10 during stages 1–2. To get a CIFAR-10 accuracy, a model needs a CIFAR-10 head: the last layer that answers "which of the 10 CIFAR-10 classes is this image?" Without one, there is nothing to score. This is the head each arm has:

ArmStage 1Stage 2CIFAR-10 head available?
ACIFAR-10 headSVHN headYes. Its stage-1 CIFAR-10 head is saved and can be reattached.
Bnone (skipped)SVHN headNo. It never trained on CIFAR-10.
CCIFAR-100 headSVHN headNo. Its head answers 100 CIFAR-100 classes, not CIFAR-10's 10.

So during stages 1–2, only A can be scored on CIFAR-10, by reattaching its old head. B and C can't: their heads answer different questions (digits 0–9 for SVHN, or 100 classes for CIFAR-100). And even for A, the old head is a weak measure: after SVHN training the backbone's features have shifted, so the old head may score ~10% even if the backbone still knows a lot.

Why every arm needs a score: A's score alone has no meaning, because any backbone trained on SVHN picks up general image features that help a little with CIFAR-10. B and C show how much. Example: A 60%, C 48%, B 38% → 22 points come from pretraining on CIFAR-10 (A − B), and 12 of them are specific to CIFAR-10 (A − C).

The fix: give every arm a temporary CIFAR-10 head. Required at two points: the end of stage 1 (before forgetting) and the end of stage 2 (the starting point for relearning). Optional every ~500 steps in between, to see how fast forgetting happens. Each time: freeze the model, train a small CIFAR-10 head on top (the linear probe), test it, then throw the head away. Same procedure for all three arms, and cheap. A gets two scores: probe (what it still knows) and old head (what it looks like it knows).

What it answers:

QuestionHow to read it
1. Does A really forget, or only look like it?In stage 2, A's old head drops to ~10% while its probe stays high → A only looks forgotten; the knowledge is still inside. Both drop → A really forgot. This is the core question of the experiment.
2. How fast and how much does each arm lose?The shape of the probe line in stage 2: a fast early drop or a slow one, and whether it levels off. Tells you how much survives and when to stop stage 2.
3. What does each arm start stage 3 with?The last probe value before stage 3, the same measure for all arms (e.g. A 60%, C 48%, B 38%). If A relearns fastest, this shows whether it simply started with more.
4. Does relearning use what was kept?High probe and fast relearning → the kept knowledge helps. High probe but slow relearning → it was there but got damaged at the start of stage 3 (check the warmup).

In one sentence: the stage-3 curves tell you who relearns fastest; the probe at checkpoints tells you why, by showing what each model actually kept through forgetting.

Pitfalls to avoid in the figures

  • A single "recovered" threshold can end up empty if no arm reaches it within the stage-3 budget. That is why steps to threshold uses several levels (50 / 70 / 80%).
  • Aligned curves can end at different lengths. Every arm gets the same number of stage-3 steps, but reaches 50% at a different time, so an arm that gets there later has less curve left. Compare slopes only over the range all arms share, or give stage 3 enough steps that every arm has the same length of curve after alignment.
  • Overlapping A-seen and never-seen lines for A would mean a small or zero memory effect for specific images. Judge it with the difference of differences (section 4), not by eye.
  • One seed is not a result. Final figures show mean ± spread over seeds.

1 · SVHN "chance" is 19.6%, not 10%

Digit 1 alone is 19% of SVHN. A model that always answers "1" scores 19.6% on the SVHN test set. Read stage-2 SVHN accuracy against that floor.

2 · C's data is close to A's, but not the same

CIFAR-100 has look-alikes for most CIFAR-10 classes (pickup truck, bus, tiger, wolf, camel, lizard), and nothing for bird or ship. So C is a fair "pretrained on similar photos, never on CIFAR-10" control.

3 · One normalization works for every stage

CIFAR-10 mean (0.4914, 0.4822, 0.4465), std (0.2470, 0.2435, 0.2616), matching the published values. CIFAR-100 is almost identical. SVHN is a bit darker and lower-contrast (shifted ~0.2 std), which is small enough to use the same values.

4 · SVHN images contain neighboring digits

The label is the center digit, but parts of other digits often show at the edges, and many crops are blurry. That is why SVHN gets crop-only augmentation: a flipped 2 or 3 is not a valid digit.

Is one normalization unfair to SVHN and CIFAR-100?

Every image is normalized with CIFAR-10's mean and std, in every stage. This is how each dataset looks after that. Perfectly matched data would be mean 0 and std 1.

DatasetMean after (R, G, B)Std afterWhat it means
CIFAR-100, 0, 01Exact, by definition.
CIFAR-1000.06, 0.02, −0.02≈1.06Almost perfectly normalized anyway. C loses nothing.
SVHN−0.22, −0.16, 0.10≈0.8Off by about 0.2 std: small. ResNet-18's BatchNorm layers re-center their inputs during training, so the network adapts easily.

Why one fixed normalization: it is part of the model's input, so keeping it fixed means only the data changes between stages, not the input scaling. Every arm gets exactly the same treatment in each stage, so the A–B–C comparison stays fair.

Decisions taken from these findings

DecisionWhy
Normalize every stage and arm with the CIFAR-10 mean/std aboveInputs mean the same thing in every stage; the other datasets are close enough.
Report stage-2 SVHN accuracy next to the 19.6% floorUnbalanced classes make 10% the wrong baseline.
CIFAR: random crop (padding 4) + flip · SVHN: crop onlyChecked visually: crops keep objects recognizable, flips break digits.
Split CIFAR-10 per class (equal counts in every subset)The data is perfectly balanced, so no subset should end up light on any class.

14 · The saved splits

Which images go where, fixed once

src/make_splits.py picked these once and saved only the image numbers (indices) to data/splits.npz. Every run of every arm and seed reads the same file, so the groups never change.

CIFAR-10 train  50,000
├── c10_pretrain     40,000   4,000 per class   A learns these in stage 1
│   └── a_seen_seed1…5  5,000   500 per class     stage 3 "A-seen", a different 5k for each seed
└── held out     10,000                     no arm trains on these in stages 1–2
    ├── c10_val         5,000   500 per class     choosing settings (calibration)
    └── c10_never_seen  5,000   500 per class     stage 3 "never-seen" + the linear probe

CIFAR-100 train  50,000
└── c100_pretrain    40,000   400 per class     C learns these in stage 1

SVHN train and all test sets are used whole: no split needed.

How they were made

  • Per class: one helper, take_per_class, picks N random images of every class and returns the rest. Every split is built from it.
  • Fixed seed (0) for the pools, so they are the same forever.
  • Its own seed per A-seen group (1–5), so adding a seed never changes the others.
  • C gets 40k too, the same amount of data as A; only the content differs.

Checked automatically

  • Right size, no image twice, equal count for every class.
  • Pretrain, validation and never-seen don't overlap and cover all 50k.
  • Every A-seen group lies inside the pretrain pool; no two seeds share a group.
  • Built twice → identical. Rerunning gives the exact same file.
  • The script refuses to overwrite an existing splits.npz.

Good to know: data/ is not in git, so the file lives only on this Mac. If it's lost, rerunning python src/make_splits.py recreates exactly the same splits, as long as the seed and per-class numbers are never changed.

Rules built in

  • Augment only for training. Evaluation, validation and the probe always get plain images.
  • Splits come from the training sets, so validation and never-seen load train=True with augmentation off.
  • The seed fixes the shuffle order: same seed, same order; tested.
  • One normalization (CIFAR-10 mean/std) for everything.
  • Batch 128, 4 workers kept alive between epochs, no pin_memory (not on MPS).

When writing run scripts

The loaders start 4 worker processes, and on macOS each one re-runs the script that started it. So every script that uses them must keep its code under if __name__ == "__main__":, or the workers crash.

16 · The model

ResNet-18 for small images, with named heads (src/model.py)

New to CNNs? How a CNN sees a picture walks through filters and feature maps with a tiny 7×7 example.

The backbone: what happens to one 32×32 image

PartShape out (channels × size)LearnsLearnable numbers
input3 × 32 × 32red, green, blue—
stem: 3×3 conv, stride 1 (changed from 7×7 stride 2)64 × 32 × 32edges, colour spots1,856
max-pool (removed)64 × 32 × 32—0
layer1 · 2 residual blocks64 × 32 × 32corners, curves, simple textures147,968
layer2 · halves size, doubles channels128 × 16 × 16textures, small parts525,568
layer3256 × 8 × 8object parts2,099,712
layer4512 × 4 × 4whole-object patterns8,393,728
average pool → features512"which patterns are present"0
total backbone11,168,832

Why the stem is changed: the original ResNet-18 is built for 224×224 photos and shrinks the image 4× straight away; a 32×32 image would be 8×8 before any real learning, and 1×1 at the end. With the small stem, layer4 still has a 4×4 map. Typical CIFAR-10 accuracy goes from ~87% to ~93–95%.

Residual blocks: each block adds its input back onto its output (output = ReLU(F(x) + x)), so it only learns an improvement, and the training signal reaches the early layers. That is what makes 17 conv layers trainable.

The heads: one per question, one active at a time

ArmStage 1Stage 2Stage 3Heads in the final checkpoint

How to use it

  • net.add_head(name): new random head, becomes active.
  • net.set_head("cifar10"): switch to A's old head for the old-head test, then back to "svhn".
  • net(x): scores from the active head. net.features(x): the 512 features, for the probe.
  • net.train() while training, net.eval() for any measurement (BatchNorm).

Guarantees (tested)

  • Adding a head that exists is refused, so A's trained head can't be wiped.
  • An inactive head stays exactly unchanged during training (checked after SGD steps with momentum and weight decay).
  • New heads go to the model's device (MPS) automatically.
  • Checkpoints include every head.
17 · Training, measuring and saving

One loop for every stage (src/train.py, evaluate.py, utils.py)

Stages differ only in their settings. The loop counts in steps (one step = one batch of 128); run scripts turn epochs into steps (epochs × steps per epoch, e.g. 40k ÷ 128 = 313 steps per epoch). The run script also decides what to measure and passes it in as measure(step), so the loop never changes.

Stage 1Stage 2Stage 3
Lengthepochs × 313 steps (epochs still to choose)fixed number of SVHN steps (calibration)fixed step budget (calibration)
Learning ratecosine from 0.1cosine from 0.1warmup, then constant
Trainsbackbone + cifar10 / cifar100 headbackbone + svhn headbackbone + relearn head
measure(step)test acc + loss every epochSVHN test · A's old head · probeCIFAR-10 test, dense early

The optimizer

  • SGD, momentum 0.9, weight decay 5e-4, batch 128 (configs/base.yaml).
  • Built fresh for every stage: SVHN momentum never leaks into stage 3.
  • Holds the backbone + active head only. Inactive heads are not in it at all, so A's old head can't move (tested).

Measuring (evaluate.py)

  • evaluate(net, loader, device) → accuracy and loss over every image.
  • Always eval mode + no gradients: measuring never changes the model, including BatchNorm statistics (tested).
  • Loss summed per image, so the smaller last batch isn't over-weighted. Matches an independent calculation exactly.
  • evaluate_head(..., "cifar10") for A's old-head test; always switches back.

What one log line looks like

{"step": 313, "epoch": 1.0, "lr": 0.0999, "train_loss": 1.62, "train_acc": 0.41, "seconds": 28.4, "test_acc": 0.52, "test_loss": 1.33}

train_loss and train_acc are averaged since the previous line; everything after seconds is whatever measure(step) returned. Read a whole log with pd.read_json(path, lines=True).

Provenance: every result says how it was made

  • Fingerprint of splits.npz (now f3308e9a4aafd2c0), the device (type and GPU name), PyTorch / torchvision / Python versions, date.
  • Loading stops if a checkpoint was made on the other kind of device (MPS vs CUDA).
  • The full config used.
  • Loading stops if the split on disk isn't the one a checkpoint was trained with.
  • Checkpoints are loaded safely: the file can't run code.

Crash-safe

  • A resume file every N steps, written to .tmp then renamed, so it's never half-written.
  • Rerun the same command → it continues from the last resume step. Tested: stopping and resuming gives exactly the same weights (with the same batches).
  • Log lines after the resume point are removed, so each step appears once.
  • A loss of NaN/inf stops the run immediately.
